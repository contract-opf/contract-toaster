# mypy baseline — issue #65 (diagnostic G4 / action B4).
#
# THIS LIST CAN ONLY SHRINK.
#
# Every path below is a module that did NOT type-check under `[tool.mypy]`
# `strict = true` on the commit that introduced the gate. Each one also has a
# matching `[[tool.mypy.overrides]] ignore_errors = true` entry in
# `pyproject.toml`, which is what keeps `mypy` green while the debt is paid
# down module by module.
#
# THE RATCHET, and how it is enforced (tests/test_lint_gates_65.py, check 4):
#
#   * Every `[[tool.mypy.overrides]] ignore_errors = true` module in
#     pyproject.toml must appear here. You cannot silence a NEW module without
#     also writing it down here, in the diff, where a reviewer sees it.
#   * No path here may be one that mypy now PASSES. The test re-runs mypy with
#     the `ignore_errors` overrides stripped out and compares. So the moment
#     you actually fix a module, this gate goes red until you delete its line
#     here AND its override in pyproject.toml — which is the only direction
#     this file is allowed to move.
#
# Paths are repo-relative POSIX paths, one per line, sorted. `#` comments and
# blank lines are ignored.
#
# PATH -> OVERRIDE MODULE NAME. An override entry names a MODULE, not a path,
# and mypy derives that name by walking up from the file for as long as the
# directory holds an `__init__.py`. `backend/src/__init__.py` exists, so
# `backend/src/reviews.py` is the module `src.reviews`; `scripts/` has no
# `__init__.py`, so `scripts/opf_load.py` is simply `opf_load`. Get that wrong
# and the override silently matches nothing while mypy stays red — which is
# how the first cut of this file was written. tests/test_lint_gates_65.py
# re-derives the names by the same rule and asserts they are unique, because
# two files deriving the same module name would let one override silence both.
